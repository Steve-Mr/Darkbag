# S1 补丁证据包 — 修正探测的两处测量缺陷

- 类型：S1 事后修复（不新增阶段，不改采集路径）
- 分支：`feat/true-zsl-capture`
- 触发：一台 Motorola XT2409-5 的真实探测报告
- 时间：2026-11-17

## 1. 触发报告（节选）

```json
{"verdict":"UNSUPPORTED","failures":["COPY_SLOW","METADATA_MISS"],
 "sample":{"rawFrameCount":121,"rawFps":30.25,
   "gapP50Ms":33.479,"gapP95Ms":33.479,"gapMaxMs":33.479,
   "ageP50Ms":68.16,"ageP95Ms":100.93,
   "copyP50Ms":10,"copyP95Ms":29,
   "previewFpsBaseline":0,"previewFpsDual":30,"previewDropRatio":0,
   "metadataHitRate":0.0248,"warmupMs":221,
   "thermalStatusBefore":0,"thermalStatusAfter":0,"captureFailures":0}}
```

RAW 流本身非常健康：30.25 fps、帧间隔恒定 33.479 ms、帧龄 68–101 ms、无 capture 失败。
两个失败码中，`METADATA_MISS` 与 `previewFpsBaseline=0` 均来自**测量方法错误**，不是设备缺陷。

## 2. 缺陷一：W0 基线预览恒为 0

**根因**：W0 期间 repeating 请求仍由生产回调（`CameraHardwareStreamController.handleCaptureResult`）驱动，
结果只写入 `captureResultFlow`，**不会**调用探测适配器的 `onPreviewResult`；适配器的回调只在
`beginDualStream()` 里替换 repeating 时才安装。因此 `previewFpsBaseline` 恒为 0，
`previewDropRatio` 因分母为 0 恒为 0，`PREVIEW_DEGRADED` **永远不可能触发**（对所有设备都是假阴性）。

**修复**：
- 新增 `camera/session/zsl/ZslProbeMeasurementsTap.kt`
  - `ZslProbePreviewTap`：`setFrameObserver` 时订阅 `captureResultFlow`，以订阅时刻 replay 尾帧的
    `SENSOR_TIMESTAMP` 为截断点，只计 live 帧；`isDualStreamActive()`（即 `begun`）为真时让位给
    适配器回调，避免 W1 双计。
  - `shouldCountBaselinePreview(ts, cut, dual)`：纯函数，单测覆盖 replay 排除与双流让位。
- 适配器 `setFrameObserver` 改为 start/stop 该 tap；W1 回调保持直接上报。

## 3. 缺陷二：元数据绑定按"回调瞬时查表"判定

**根因**：`handleRawImage` 在 RAW 回调里立刻 `findCaptureResultSync(image.timestamp)`，而 HAL 允许
`CaptureResult` 晚于图像投递。该设备 2.5% 的命中率（121 帧命中 3 帧）与 100 ms 级帧龄一致，
说明结果只是**晚到**，不是缺失。

**修复**：
- 端口 `ZslProbeFrameObserver.onRawFrame(timestampNs, copyMs)` 去掉瞬时 `metadataHit`；
  新增 `ZslProbeSession.metadataBinding(timestampsNs): ZslMetadataBinding`。
- 控制器在 **W2 settle window 结束后**统一回查（W2 的 1000 ms 同时充当结果落地的 grace window），
  回查失败/端口异常按"未绑定"保守处理，不会因异常而放行。
- 适配器用 `ZslProbeMetadataBinder`（精确 + 5 ms 容差）逐帧回查；纯函数可单测。

**语义变化**：`metadataHitRate` 现在表示"窗口结束后，该帧能否绑定到自己的 `CaptureResult`"，
符合真实需求（合并归一化、WB/CCM/EXIF 都依赖它），而不是"回调同一瞬间是否已到达"。
`ZslProbeSample` 字段不变，但**报告 schema 升至 v3**：旧 v2 报告（旧口径）一律失效并回到「未检测」，强制重测。

## 4. 测试

| 套件 | 新增/变化 | 覆盖 |
|---|---|---|

全量：**110 suites / 727 tests / 0 failures / 0 errors / 0 skipped**（修复前 719；+8：tap 4、controller +3、report +1）。

> **schema 升到 3**：`metadataHitRate` 口径变化，旧 v2 报告（含触发本修复的那份）一律判失效，设置页回到「未检测」，必须重测；避免同版本号承载两种语义。

## 5. 对触发设备的预期（不是结论，需重测）

修复后该机预计只剩 `COPY_SLOW`（copyP95 29 ms > SUPPORTED 上限 12 ms）→ 仍为 `UNSUPPORTED`，
但失败原因会变得**单一且真实**；RAW 帧率 30.25、间隔恒定、帧龄 101 ms 均满足 SUPPORTED 档。
即：这是"风险性强制启用"的合理候选（降档 depth=2/15fps 摊薄拷贝成本），但仍需真机重测确认
`previewDropRatio`（修复后才第一次真正被测量）。

## 6. 已知未覆盖

- 适配器内部的 `ZslProbePreviewTap` 与真实 `captureResultFlow` 的联调只能在真机验证
  （单测覆盖纯判定与绑定逻辑，不覆盖 Coroutine 订阅时序）。
- W2 作为 grace window 的 1000 ms 是否足够，取决于设备的 result 延迟分布；若重测仍出现
  低于 97% 的绑定率，再评估是否延长 settle 或改为"按到达延迟容忍"。
