# S1-FIX-R2 — 拷贝判据由绝对耗时改为带宽口径

日期：2026-11-18
阶段：S1-FIX-R2（S1 探针判据修正）
报告 schema：v3 → **v4**

## 1. 触发问题

真机探针报告（`version: 3`）在本机 Moto XT2409-5（`motorola/XT2409-5/36`，lens 0，
4096×3072）上产出 **UNSUPPORTED / `COPY_SLOW`**，但除拷贝外所有指标都是优质值：

| 指标 | 实测 | SUPPORTED 门限 | 结论 |
|---|---|---|---|
| `rawFps` | 29.5 | ≥15 | 通过 |
| `gapP95Ms` / `gapMaxMs` | 33.479 / 33.479（恒定） | ≤1.8× / ≤6× 标称 | 通过（零抖动） |
| `ageP95Ms` | 78.582 | ≤140 | 通过 |
| `metadataHitRate` | **1.0** | ≥0.97 | 通过（S1FIX 修复已生效） |
| `previewDropRatio` | **0** | ≤0.20 | 通过 |
| `warmupMs` | 225 | ≤400 | 通过 |
| `thermalStatusBefore/After` | 0 / 0 | ≤2 | 通过 |
| `captureFailures` | 0 | ≤1 | 通过 |
| **`copyP95Ms`** | **15.15** | **≤12** | **✗ 唯一失败** |

## 2. 根因：门限本身不可达，且与分辨率耦合

`copyP95Ms` 量的是单帧 4096×3072×2 = **24 MiB** 的 `copyBayerWithStride` 耗时。换算吞吐：

- P50 = 9 ms → 24 MiB / 0.009 s ≈ **2667 MiB/s**
- P95 = 15.15 ms → 24 MiB / 0.01515 s ≈ **1584 MiB/s**

就这一台设备（moto XT2409-5，**n=1**）而言，该吞吐与 LPDDR5 内存带宽上限同量级，属于正常水平；
是否为该档位机型的普遍表现仍需多机采样确认。

而旧门限 `RECOMMENDED ≤6 ms / SUPPORTED ≤12 ms`：

- 6 ms 意味着 **4000 MiB/s** 的单核拷贝吞吐，约等于桌面 DDR5 量级，当前移动端 SoC 难以企及；
- 因此该门限**大概率在任何设备上都只会产出 `COPY_SLOW`**，是一条实际不可达的门限
  （依据内存规格推断 + 本机 n=1 实测，非多机采样）；
- 其来源是 `HdrPlusStreamingBurst.kt` KDoc 中"~2ms"的**未经验证估计**（同文 §1.3 原文即标注
  `` `[需实测]` ``）。2 ms 对应 12288 MiB/s，比实测快一个数量级。

此外，绝对毫秒门限天然绑定分辨率：同一块内存跑 50 MP 帧时耗时必然约为 12 MP 的 4.17 倍，
即便内存性能完全相同也会被判失败。

## 3. 修正

### 3.1 判据口径

`COPY_SLOW` 改为吞吐（MiB/s）判定，取 **P5 吞吐**：对**逐帧吞吐**取 5% 分位，即最慢那批帧的
吞吐下限。它与「耗时 P95 的倒数」方向一致、数值接近，但**并不等价**——先取耗时分位再求倒数会在
分位点处非线性放大，且可能被个别异常帧主导；实现是逐帧求吞吐后再取分位
（`ZslProbeMeasurements.kt` 的 `copyThroughput()`）。**不要**改回 `1 / copyP95Ms`：

历史门限（v3 及以前，已废弃）：`RECOMMENDED ≤ 6 ms` / `SUPPORTED ≤ 12 ms`。保留此行仅为解释上述复现；
对 24 MiB 帧它们分别等价于 4000 / 2000 MiB/s，前者无手机可达。

| 档位 | 门限 | 依据 |
|---|---|---|
| RECOMMENDED | ≥ 1800 MiB/s | 略高于本机实测 P5 吞吐（1584 MiB/s；P50 2667 MiB/s，**n=1，待多机补充**）；1800 对应 13.3 ms ≈ 40% 帧预算，可支撑 `ringDepth=3` |
| SUPPORTED | ≥ 900 MiB/s | 30 fps 帧预算 33.3 ms 对应 24 MiB / 33.3 ms ≈ 717 MiB/s 是**绝对下限**；900 留出约 2/3 帧时间余量给 HAL/回调/预览 |

边界含等号：吞吐 `== 门限` 视为达标（与其余阈值一致）。

### 3.2 测量精度

- `ZslProbeFrameObserver.onRawFrame` 第二参数由 `copyMs: Long`（**整毫秒截断**）改为 `copyNanos: Long`。
  整毫秒下 15 ms 与 15.9 ms 同值，却对应 6% 的吞吐差，无法支撑带宽判定。
- 新增 `copyFrameBytes`（宽×高×2）参与换算；`ZslProbeSample` 新增
  `copyThroughputP5MiBps` / `copyThroughputP50MiBps`。
- 逐帧先求吞吐再取分位（而非先取耗时分位再求倒数），避免非线性放大与单帧异常值主导。
- 零/负耗时按 0 处理，杜绝除零产生 `Infinity` 污染评分。

### 3.3 缺失语义（复审 MAJOR-3 修正）

吞吐为 0 有两种来源，**必须区分**：

- `copyThroughputMeasured = false`：单帧字节数未知（`session.capabilities` 读取失败，
  `ZslProbeController` 以 `runCatching{}.getOrNull()` 吞为 null）。这是**阈值未知**，
  不归咎于拷贝慢，判 **`COPY_UNMEASURED`**（新增失败码），文案 "Could not measure copy speed / 无法测量拷贝速度"，
  sheet 指标行显示 `unknown` 而非 `0 MiB/s`。
- `copyThroughputMeasured = true` 且吞吐确为 0：**已知不可行**，判 `COPY_SLOW`。

两者结论都是 UNSUPPORTED 并建议重测（**不**沿用 `warmupMs == null` 的乐观放行），差异只在原因码与文案。

> 注意："无 RAW 帧"这半句**不会**经由评分层触发——`ZslProbeController` 在 `rawFrameCount < MIN_RAW_FRAMES`
> 时已在评分前短路为 `RAW_FPS_LOW`，所以评分层看到的必然是"有帧但字节数未知"这一种情形。

`copyP50Ms` / `copyP95Ms` 仍然统计并写入报告，只供诊断，不再参与判定。

### 3.4 Schema

`ZslProbeReport.SCHEMA_VERSION` 3 → **4**：判据口径变了，旧 v1–v3 报告按"无报告"处理，
设置页回到 "Not tested" 并要求重测。

### 3.5 附带修正

`HdrPlusStreamingBurst.addFrame()` 的 KDoc 中"~2ms"改为实测数据；
`docs/TRUE_ZSL_CAPTURE_FEASIBILITY_AND_DESIGN.md` §1.3 同步更正并移除 `` `[需实测]` `` 标记。

## 4. 预期结果

同一份 report 在新口径下：

- 吞吐 P5 ≈ 1584 MiB/s ≥ 900 → **不再 `COPY_SLOW`**；
- `warmupMs = 225 > 200` → 无法达 RECOMMENDED；
- 结论 **SUPPORTED**，`RingConfig(depth=2, targetFps=24, minValidFrames=2)`。

该场景已固化为回归测试 `ZslProbeVerdictTest.testMotoXt2409RealReportIsSupportedNotCopySlow`。
