# PR #298 第九轮：历史核查 —— "增益进管线"到底发生过没有？附带更正上一轮的一条建议

> 触发问题：*"把 digitalGain 移到 Halide 管线内似乎在之前的 commit 中出现过但是又出现似乎其他问题还原了？"*
> 只读分析，未改动既有产物。

---

## 1. 核查结论：**"digitalGain 进 Halide" 从未发生过**

我把**历代** Halide 管道调用实参都查了一遍（`git log --all -p -S 'hdrplus_*_pipeline(inputBuf'`），所有版本都是：

```cpp
hdrplus_raw_pipeline(inputBuf, bl_r, …, ccmHalideBuf, /*compression=*/1.0f, /*gain=*/1.0f, outputBuf);
```

- 生成器里 `Input<float> compression{"compression"}` / `Input<float> gain{"gain"}` 自最初集成（`b4e49463`）就存在，但**从来没有被喂过真实数值**（永远是 1.0f）；
- 搜索 `digitalGain, outputBuf` / `gain, outputBuf` 均**零命中**；
- `compression` 唯一被用过一次，是 `c33cff8e` 在**显示域**的 `highlight_compress`（不是把 digitalGain 移进管线），随后被 `e97058e8`/`47819f26` 删除。

→ 所以**没有任何东西需要"恢复"**；当前管线里这两个输入是死参数。

---

## 2. 你记得的那次改动：是 **ColorPipe 里的 `<<2`（×4）增益**，且确实"改了又被还原"

当时的架构：**Halide 输出是 14-bit 尺度（0.25×）**，ColorPipe 用左移 2 位（×4）把亮度补回 16-bit，并配 `min(v,16383)` 钳制防止移位前溢出。

| 时间 | 提交 | 做了什么 | 结局 |
|---|---|---|---|
| 2026-06-21 | `41ba3703` | "Fix DNG and JPEG highlight clipping by removing erroneous 14-bit bounds clamping"：**删掉 `<<2` 与 16383 钳制**，并注释"Halide 输出已是 16-bit" | **被 revert 两次**：`a92eb380` → `52c34bcc`（PR #262 `79ad3b40`）❌ |
| 2026-06-21 | `69b1034c` | 同类尝试的温和版：`<<2` → `× 4.0f` | 未合并 ❌ |
| 2026-08-04 | `31b98160`（**主线**） | 去掉 JNI 侧 `min(v,16383)` 等 14-bit 钳制 | ✅ |
| 2026-08-06 | `dd04cb72`（**主线**） | **把管线归一化从 16383 改成 65535** | ✅ |
| — | 现状 | ColorPipe 里已无任何移位/增益（纯 float 读取） | ✅ |

**为什么当年必须回滚**：增益与归一化**是耦合的**（0.25× 的输出需要 ×4 才能回到正常亮度）。`41ba3703` 只删增益/钳制、管线仍输出 0.25× → 整幅暗 4 倍（并连带高光钳制行为变化），所以被回滚；**正确顺序是先在管线内把归一化改成 16-bit，再撤掉显示侧的 ×4** —— 也就是 8 月才在主线完成的两步。

**对当前的教训（重要）**：不要把我第八轮说的"增益搬进管线"理解成"把 digitalGain 乘进共享的 Halide 输出"——那会踩同一个坑：
- 同一块 buffer 还要写 DNG（u16 容器），乘 4.66× 会**在 DNG 里削顶**；
- 且 DNG 已声明 `BaselineExposure = 2.2~2.8 EV`，再乘增益等于**重复补偿**，第三方转换器会把 DNG 渲染爆。

## 3. 更正：我第八轮那条"缩放 knee 阈值即可消除高光削顶"**不成立**

用同一次拍摄（19:57 HDR+ DNG）做三种处理的模拟（gain 4.66 + 各自的 knee + Uchimura + sRGB）：

| 处理 | 8bit G ≥250 占比 | 极大值 |
|---|---|---|
| ① 现状：knee@50000（未增益域）+ 显示域 gain | 4.79% | 255 |
| ② 建议：knee 阈值随增益缩放（50000/4.66） | **4.75%** | 253 |
| ③ 备选：DNG 路径完全去掉 knee | 4.79% | 255 |
| 参考：实测 App JPEG（现状） | 4.82% | 255 |
| 参考：非 HDR+（gain=1，knee 不变） | 0.00% | 248 |

→ **缩放/删除 raw 域 knee 对显示域饱和几乎没有影响**（4.79% → 4.75%）——我上一轮把主因判错了。

**真正的主因是"显示域增益 + 色调曲线肩部长度"**：欠曝 2.2 EV 意味着场景范围
`[名义白 1.0 … 传感器饱和 4.66]` 必须由曲线来映射，而两条曲线对这一段的"预算"不同：

| 场景线性值 | Uchimura → 8bit | ACES fit → 8bit |
|---|---|---|
| 1.00（名义白） | 0.887 → **226** | 0.804 → **205** |
| 2.00 | 0.992 → 253 | 0.915 → 233 |
| 3.00 | 1.000 → **255** | 0.954 → 243 |
| 4.66（传感器饱和） | 1.000 → **255** | 0.982 → **250** |

- Uchimura 只用了 **29 个码值**表达这 2.2 EV 的余量（场景 ≈3.0 就到 255）；
- ACES fit 用了 **45 个码值**（1.6× 的过渡层次，最高只到 250）。
→ **换 ACES fit 会让高光过渡明显更平滑**（代价：名义白更暗/整体更平），这是你可以立刻在设置里验证的。

## 4. 修正后的建议（高光部分）

| 顺序 | 措施 | 依据 |
|---|---|---|
| 1 | **降低默认欠曝**（低 ISO 下 −3 EV → −1～−1.5 EV） | 非 HDR+（gain=1）实测 0% 饱和、色比更中性；余量越小，现有曲线越从容 |
| 2 | **用肩部更长的曲线**：先试 ACES fit（设置项 mode 3）；长期做一条**按当次曝光余量参数化**的曲线（GCam 式） | §3 表格：25 → 45 码值的过渡差 |
| 3 | raw 域 knee 是否保留，按**DNG 线性性**决定（建议去掉），而**不要**指望它解决显示域饱和 | §3 模拟（4.79% vs 4.75%） |
| 4 | **不要**把增益乘进共享 Halide 输出（DNG 会削顶 + 与 BaselineExposure 重复） | §2 历史教训 |

> 第八轮其他结论仍然成立且未受影响：HDR+ 与非 HDR+ 的**暗部色偏差异**（最暗档 R/G 0.520 vs 0.828、场区 0.816 vs 0.892）来自欠曝放大加性误差；HDR+ 的 linear DNG **缺少平台级完整标定**（同一 App 的非 HDR+ Bayer DNG 反而有 CM1/2 + FM1/2 + 双光源）。
